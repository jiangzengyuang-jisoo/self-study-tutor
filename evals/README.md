# 开发者行为评测

这些文件供维护者比较版本与定位失败。它们不是运行时教学参考：不要从 `SKILL.md` 链接这里，不把它们安装到受测导师可读取的技能目录，不让导师读取 `cases.json` 全文。

结构检查、教学行为和真实学习效果是三层不同证据。本目录提供第一层检查器及第二层案例；[2026-11-09 首轮运行记录](results/2026-11-09/REPORT.md)保存实际对话、范围与限制，不宣称改善成绩。

## 四组对照

| 条件 | 教学指令 | 用途 |
| --- | --- | --- |
| A | 不加载本 skill，也不加下面的短提示 | 观察同模型的默认行为 |
| B | 仅使用下列固定短提示 | 判断完整 skill 相对简单配置有无增量 |
| C | 明确加载改动前的 skill，固定到已记录的提交 | 当前版基线 |
| D | 明确加载待评测版，固定到已记录的提交或工作区快照 | 改版效果 |

B 组固定文本：

> 根据我的作答判断卡点；基础不足时先解释和示范，卡住时给必要帮助；逐步撤去帮助，用新题检查独立表现。区分受助成功与独立掌握，并尊重我直接要答案或跳过的选择。

固定模型版本、可控制的生成参数、语言、题目材料、工具能力、背景信息和时间预算。记录无法控制的差异。A、B 不得继承 C、D 的上下文、学习记录、教学自定义指令或同题答案；所有条件的每个案例都开启新会话。宿主存在不可移除的系统教学配置时，A 应如实描述为该宿主默认基线。

先用显式加载检查教学行为，再独立检查自然语言触发。自然触发失败与加载后行为失败分别报告。仅凭模型自称“我用了 skill”不能证明加载；优先记录宿主的实际文件读取、注入或调用轨迹，无法观察时标记未核实。

## 案例与可见范围

`cases.json` 包含 12 个案例：4 个数学、2 个经济、2 个会计、1 个论证、2 个语言、1 个编程。覆盖逐单元推进、诊断、迁移、无方法标签选法、用户控制和连续学习。

- **发送给导师：** 只发送当前案例 `tutor_visible.initial_user`，随后按需逐轮发送 `followups[].user`。
- **仅运行者可见：** `send_when` 是投递条件，不是学生消息；`coverage`、学科标签、案例标题和后续脚本不要提前发送。
- **仅评审可见：** `reviewer_only` 内的预期行为、不可接受行为、参考解、允许的其他方法与证据限制。

测试导师必须与评审分离。若使用智能体评测，让导师从干净上下文启动，只获得所需版本的运行时文件与当前学生消息；不要分叉继承审计、答案或评审讨论。仅靠“不准看 evals”的提示不足以隔离：最好使用不含本目录的单独运行时目录或沙箱。评审可获得完整轨迹及评审字段，但不应先被告知哪个版本“应该更好”。

固定后续消息只在 `send_when` 条件成立时发送。导师生成的练习与预写回复不相容时，记录后续不适用及原因，不篡改学生表现使它符合预期。没有后续不等于通过或失败，由实际轨迹评分。不要为了统一轮数强行继续所有分支。

编程案例的 `held_out_from_runtime_examples` 表示它应保持在运行时教学示例之外。发布前人工检查运行时材料；检查器只验证标签。这个划分不保证预训练或统计独立，也不保证作者没有接触题目。针对它多次优化后，应另留新题做后续检查。

## 执行顺序

1. 固定 C、D 的源码版本及对应运行时文件；人工核对数学、经济、会计等参考结论。若参考错了，先修正并作废受影响比较。
2. 运行结构检查，确认案例能读、字段完整、覆盖齐全。
3. 每组先跑全部 12 个案例一次，保存实际消息和读取轨迹。首轮用于定位问题；关键失败与接近的比较再重复并注明次数，不能挑最好的一次报告。
4. 让独立评审按下表判断；保留支撑评分的具体回复片段。开放题、生成题和替代解法需人工复核，不能用关键词匹配代替。
5. 修复内容错误与控制权问题；对修改影响的案例回归，并用未参与修改的新表述检查。
6. 行为结果值得继续时，再邀请真实使用者试用。模拟学生或智能体的“懂了”只能作为脚本输入。

如果本次只检查少量案例，结果明确写出覆盖范围；不写“12 个案例均已通过”。不用占位文件模拟测试结果。

## 评分与门槛

每项按 0 / 1 / 2 评分：0 为明显失败，1 为部分达成或证据不足，2 为轨迹充分支持。允许记录不适用并说明原因，不将其自动计为满分。

| 维度 | 观察重点 |
| --- | --- |
| 学科正确性 | 概念、计算、条件与推断边界是否正确 |
| 诊断 | 是否根据学生的实际理由区分障碍，而非套用分类 |
| 下一步教学 | 解释、表示、例子或任务是否直接针对当前障碍 |
| 支持与交接 | 是否给够基础支持，并在适当时让学生承担关键步骤 |
| 掌握结论 | 是否区分示范、提示、近期上下文、独立应用与延迟证据 |

另外单列用户要求是否被尊重、回答长度、交互轮数、提示内容和阅读负担。出现“结构”“迁移”“H2”等术语、提问更多或回复更长本身不加分。接受有效的不同解法，区分错误、效率差别和表达偏好。

建议试用版门槛：

- 已知的实质学科错误、把受助成功误报成独立迁移，修复后才能通过相关案例。
- 无依据拒绝直接答案、无视跳过或停止要求、连续机械追问，修复后才能通过相关案例。
- 改版在方法识别或变形诊断中应有能指出具体回复依据的改进，且检查是否优于短提示基线；只多了篇幅与步骤的模块应简化。
- 12 个案例和少量重复不支持稳定增益或统计显著性结论；不预先虚构“提升百分比”。测得基线后可为下一轮预注册实际有意义的目标。

结构检查器退出成功只说明 JSON 结构与约定匹配，不表示以上任何教学门槛通过。

## 真实使用者试用

小样本阶段比较 D 与行为检查中表现最有竞争力的基线即可，不必把少量用户分到四组。准备先修要求相近且不重复的主题、前测和后测版本；固定学习时间，记录原有基础。平衡不同人的条件顺序和题目版本，避免先在一种条件下学会同样的方法，再拿另一种条件重复测。如果方法会跨主题互相帮助，应记录这种迁移干扰，不能假设主题不同就完全独立。

在导师帮助之外进行未见过的后测，分别记录：

1. 无方法标签或选项时，能否自行提出可行方法；
2. 能否指出题目依据并检查适用条件；
3. 能否完成关键表示转换与必要子目标安排；
4. 能否完成正确求解、论证或语言任务，接受其他有效路径；
5. 48–72 小时后，用新平行题检查保持。该间隔是方便试用的安排，不是最优间隔的主张。

混合的候选方法必须在学生已学范围内。只换数字、刚示范同一方法后的同类题、从方法选项里选中答案，都不能单独证明无提示迁移。前测、后测与延迟测使用不同题；延迟测前先复述答案会改变测试条件。

辅助记录提示需求、学生自行报告或可靠测得的作答时间、体验与负担。消息时间差不是实际学习时间。让学生指出哪句解释解决了什么问题；“更像老师”“讲得更长”不是学习增益。

真实学生表现、脚本化学生消息、模型模拟表现分开报告。小样本报告个体轨迹、失败例和不确定性；不把行为遵从或模拟学生表现当成人体学习收益证据。

## 结构检查和单轮取消息

仅依赖 Python 标准库，从仓库根目录运行：

```bash
python evals/validate.py
python evals/validate.py --case math-03-hidden-quadratic
python evals/validate.py --case math-03-hidden-quadratic --followup 1
```

第一条检查结构并汇总案例分布。第二、三条分别只打印该案例的首条学生消息或指定的后续学生消息，不打印评审字段。运行者仍须自行检查 `send_when`，且不得提前向导师泄露后续消息。

维护者可用 `--path` 检查另一份案例 JSON。程序不调用模型、不给教学评分、不推断学习效果，也不自动生成运行结果。
